# 系統 BUG 審閱報告（2026-09-13）

## 1. 報告目的

本報告針對 `tw_chip_analyzer` 現有程式進行靜態審閱與局部可重現驗證，重點檢查：

- BUY／WATCH／HOLD／REDUCE／EXIT／AVOID 決策是否符合專案鐵則。
- Chip Score、進場條件、風險報酬與市場狀態是否使用正確資料。
- 每日盤後流程是否能正確處理外部資料源失敗與缺漏。
- 除權息、減資、停牌等情況是否污染掃描與回測。
- 回測及前瞻驗證是否存在 look-ahead bias（偷看未來）或統計偏誤。
- Shioaji 逐筆資料失敗時，系統是否能如實呈現狀態。

本次只審閱，未修改任何系統行為。

## 2. 名詞與優先級

- **RR（Risk/Reward Ratio，風險報酬比）**：預期獲利空間除以可能虧損空間。
- **EOD（End of Day）**：每日收盤後執行的匯入、特徵計算與訊號產生流程。
- **Entry Filter（進場過濾器）**：分數達標後，還必須通過的市場、價格、流動性與成交條件。
- **Strong Bear（強空頭市場）**：市場趨勢明顯偏空，依專案規則不得輸出 BUY。
- **Fail-soft（局部失敗仍繼續）**：非核心資料源失敗時，只停用該成分，不讓整個流程中止。
- **Cache（快取）**：暫存已計算結果，避免重複運算；key 不完整時可能回傳錯誤舊資料。
- **Newey–West**：修正時間序列自相關與變異數不一致的統計方法，避免 t 值被高估。
- **P0**：直接破壞核心交易建議或驗證可信度，應最優先處理。
- **P1**：可能造成資料缺漏、錯誤排名或錯誤顯示，應在下一個修正批次處理。
- **P2**：邊界情況、部署風險或長期可靠性問題。

## 3. 結論摘要

本次共整理出 15 項 BUG，以及 1 項視部署方式而定的安全風險：

- P0：5 項。
- P1：8 項。
- P2：2 項。
- 條件式安全風險：1 項（回補 API，取決於服務是否對外開放）。

最需要先處理的問題是：

1. RR 門檻目前近似恆等式，無法真正阻擋風險報酬不足的交易。
2. Strong Bear 判斷錯用加權後分數，使強空頭過濾器比設定值寬鬆。
3. 鎖死漲停條件沒有接入實際分析流程。
4. 公開分析流程沒有持倉狀態，REDUCE／EXIT 幾乎無法產生。
5. 前瞻驗證未還原公司行動，且未使用 Newey–West 修正。

在上述問題修正前，不宜把 BUY 數量、驗證頁 t 值或高分組績效當成最終策略證據。

## 4. P0：核心決策與驗證問題

### BUG-01：RR 門檻近似永遠通過

**位置**：`app/services/decision/risk.py:43-46`

目前流程先以固定 R 倍數產生 TP1，再用同一個 TP1 反算 RR：

```text
TP1 = 現價 + tp1_r × risk
RR  = (TP1 - 現價) ÷ risk
    ≈ tp1_r
```

目前 `tp1_r=2.0`、`min_risk_reward=2.0`，所以 RR gate（進場門檻）不是在衡量市場可達的上漲空間，而是在驗證自己剛設定的 TP1。除少數價格四捨五入情況外，RR 幾乎固定為 2。

**影響**：

- `RR ≥ 2` 的 BUY 鐵則形同失效。
- 若實際成交在進場區上緣，真實 RR 可能已低於 2。
- 系統可能對上方壓力很近的股票仍輸出 BUY。

**建議修正**：

- 先從價格結構推導可行目標，例如前高、壓力區或波動模型目標。
- RR 分母應以實際預計進場價到停損價計算。
- 若仍保留固定 R 倍 TP，該數值只能作為風控目標，不可同時拿來當 Entry Filter 的獨立證據。

**驗收條件**：

- 同一停損下，不同上方壓力位置能產生不同 RR。
- 進場區上緣的 RR 低於 2 時必須輸出 WATCH。
- 測試至少涵蓋 RR 低於、等於及高於門檻三種情況。

### BUG-02：Strong Bear 判斷錯用加權後市場分數

**位置**：

- `app/services/analysis.py:120-127`
- `app/services/chip/market_score.py:11-14`
- `config/thresholds.yaml` 的 `weights.market` 與 `entry_filter.strong_bear_market_score`

`market_trend_score` 原本已是 `-1..1`，但 Chip Score 的市場子分數會先乘上 `market_trend: 0.65`。分析流程之後再從 `chip.market` 還原，得到的是加權後的 `0.65 × market_trend_score`，不是原始市場趨勢。

例如：

```text
原始 market_trend_score = -0.60
送進 Entry Filter 的數值 = -0.60 × 0.65 = -0.39
Strong Bear 門檻       = -0.50
結果                    = 未阻擋 BUY
```

實際要到約 `-0.77` 才會觸發 `-0.5` 門檻。

**影響**：強空頭市場仍可能輸出 BUY；未來若啟用產業趨勢權重，產業分數還可能進一步干擾全市場 Strong Bear 判斷。

**建議修正**：Entry Filter 直接使用 `MarketContext.market_trend_score`，不要從 Chip Score 子分數反推。

**驗收條件**：原始市場分數等於或低於設定門檻時，無論 Chip Score 權重如何調整，都必須阻擋 BUY。

### BUG-03：鎖死漲停條件未接入分析流程

**位置**：

- `app/services/decision/entry.py:61-62`
- `app/services/analysis.py:122-127`

`PriceContext.is_locked_limit` 已定義且 Entry Filter 也會檢查，但建立 `PriceContext` 時沒有傳入該值，因此永遠使用預設 `False`。

**影響**：鎖死漲停、實際無法合理成交的股票仍可能輸出 BUY，違反專案 Entry Filter 鐵則。

**建議修正**：建立可測試的「漲停且無賣單／無合理成交」判斷，將結果寫入特徵或分析上下文。若 Phase 1 盤後資料不足以判斷，應保守輸出 WATCH，而不是默認可成交。

**驗收條件**：鎖死漲停案例必須輸出 WATCH，並帶有「無法合理成交」原因。

### BUG-04：REDUCE／EXIT 在公開產品流程中不可達

**位置**：

- `app/services/analysis.py:100-136`
- `app/services/decision/__init__.py:21-48`
- `app/services/decision/exit.py:20-48`
- `app/api/stocks.py:83-116`
- `app/services/market_scan.py:34-69`

決策引擎只有在 `already_in_position=True` 時才會走 Exit Logic（出場邏輯），但股票分析、scanner 與 dashboard 都沒有提供或傳入持倉狀態，實際上一直使用預設 `False`。

**影響**：

- REDUCE／EXIT 雖然存在於程式與 UI 語意中，正式分析結果基本上無法產生。
- 同一股票無法依「未持倉」與「已持倉」提供不同建議。
- Hard stop（跌破停損）與出貨警示無法在正式產品流程生效。

**建議修正**：明確選擇產品模型：

1. API 接受持倉狀態、成本、停損與持有期間；或
2. 將輸出拆成「未持倉建議」與「已持倉管理建議」兩欄。

**驗收條件**：相同股票資料在不同持倉上下文中，能分別產生 WATCH／BUY 與 HOLD／REDUCE／EXIT。

### BUG-05：前瞻驗證未還原公司行動，且 t 值未做 Newey–West 修正

**位置**：`app/services/forward_report.py:35-131`

驗證頁直接讀取 `daily_price` 原始開收盤價，沒有套用除權息、配股、拆股或減資還原因子。20 日 forward return（未來報酬）又會大量重疊，但目前仍使用一般平均值 t 檢定。

**影響**：

- 公司行動日可能產生假的巨大正負報酬。
- 重疊報酬的自相關可能讓 t 值看起來比實際顯著。
- 驗證頁與正式 backtest／SBL OOS 腳本採用不同統計口徑。
- 快取只看最新訊號日期；若價格更新但尚未產生新訊號，pending 與績效結果不會刷新。

**建議修正**：

- 與 backtest runner 共用同一套公司行動還原及 forward return 實作。
- IC 時序的 t 值改用既有 `newey_west_t`，lag 依 horizon 設定。
- 快取 key 納入最新價格日期、成本設定與 horizon／bucket 設定版本。

**驗收條件**：

- 公司行動前後的報酬序列保持連續。
- 驗證頁與離線 backtest 對同一批訊號產生一致結果。
- 新增價格資料後，即使最新訊號日不變，報告仍會更新。

## 5. P1：資料與掃描可靠性問題

### BUG-06：背離掃描快取沒有包含視窗參數

**位置**：`app/services/flow_scan.py:47-64`

快取只以 `as_of` 日期作為 key，沒有包含 `window`、`lookback_days` 或設定版本。

可重現行為：

```text
第一次請求 window=60 → 計算並快取 60 日結果
第二次請求 window=20 → 直接取出 60 日結果
API 外層仍顯示 window=20
```

**影響**：API 標示的觀察窗與實際資料不一致，可能使使用者誤判背離。

**建議修正**：快取 key 至少使用 `(as_of, window, lookback_days, config_version)`。

### BUG-07：非核心資料源故障會中止整個 EOD

**位置**：

- `app/jobs/daily.py:67-93`
- `app/jobs/scheduler.py:45-50`

排程每天固定啟用 TAIEX 與 TDCC，但兩者在核心 TWSE／TPEx 匯入前執行且沒有 fail-soft。任一來源暫時失敗，當日行情、特徵與訊號都不會繼續。

**影響**：非核心資料源短暫故障可能造成整日沒有 signal snapshot，而系統原本其實能在缺少 holder 或 market 成分時降級運作。

**建議修正**：

- TAIEX、TDCC 應各自捕捉失敗並記錄資料品質狀態。
- 僅在核心 OHLCV 不完整或橫斷面覆蓋率低於設定門檻時，停止產生訊號。
- 降級產生訊號時，API／UI 必須明確標示缺少哪些資料成分。

### BUG-08：TPEx 三個來源被綁成全有或全無

**位置**：`app/jobs/daily.py:144-155`

TPEx 行情、法人與融資資料在同一個 `try` 中依序抓取，全部抓完才匯入。若第三個融資端點失敗，前兩個已抓成功的資料也不會寫入。

**影響**：單一 TPEx 端點失敗可能讓整個上櫃市場從當日橫斷面消失，進一步改變所有股票的百分位分數。

**建議修正**：三個來源分開抓取、匯入及記錄涵蓋率；至少成功的 OHLCV 必須保留。

### BUG-09：Shioaji 錯誤被統計成成功但無資料

**位置**：

- `app/services/ticks.py:36-58`
- `app/jobs/import_ticks.py:78-90`

`get_ticks` 捕捉所有 Shioaji 例外後回傳空陣列；批次匯入收到空陣列後仍增加 `done`，不增加 `failed`。

以下狀況因此無法區分：

- 該股票當日確實沒有逐筆資料。
- Token 過期或 Session 失效。
- 網路／API 錯誤。
- Shioaji 回傳異常。

**影響**：操作介面可能顯示 `failed=0`，實際卻漏掉大量股票；由於 Chip Score 會依有無 intraday 成分分組，漏資料還會改變成分組合。

**建議修正**：回傳明確狀態，例如 `cached／fetched／empty／failed`；認證或連線失敗應重建 session，並在連續失敗時停止批次而不是繼續消耗配額。

### BUG-10：不足 5／20 日的資料仍被標示為固定視窗特徵

**位置**：

- `app/services/feature_builder.py:175-192`
- `app/services/feature_builder.py:216-243`

資料不足時，`ret5`、`avg_vol20`、法人 5 日淨額、融資券 5 日變化與 SBL 20 日變化會使用現有最早資料，而不是回傳缺值。

例如只有兩筆 SBL 資料，也可能產生名義上的 20 日百分比變化。

**影響**：新上市或缺資料股票會拿 1～2 日變化和其他股票的完整 5／20 日變化做橫斷面比較，違反可比性。

**建議修正**：

- 固定視窗特徵應要求最低有效觀測數。
- 資料不足時回傳 `NULL`，並由成分可用性機制處理。
- 若業務上需要短視窗降級值，必須使用不同欄位名稱並分組正規化。

### BUG-11：法人／信用資料缺漏被誤當成中性值 0

**位置**：

- `app/services/feature_builder.py:428-449`
- `app/services/analysis.py:71-98`

不存在的法人、融資、融券與 SBL z-score 會寫成 `0.0`，但 institutional 成分永遠被列為 active（可用）。系統因此無法分辨真正中性與資料缺漏。

**影響**：

- 部分匯入失敗、新上市或無資料股票可能獲得不應存在的 institutional 分數。
- 不同資料完整度的股票被放在同一成分組合中做百分位排名。
- 可能重現先前 intraday／TDCC 混排造成的尺度偏差。

**建議修正**：原始缺值保持 `NULL`，並另外記錄 institutional 子來源的有效性；依實際可用成分分組映射。

### BUG-12：市場漲跌家數未做公司行動還原

**位置**：`app/services/market_score.py:23-47`

市場 breadth（漲跌家數廣度）直接比較今日與前一交易日原始收盤價。除息、配股、拆股或減資造成的機械價格差異會被當成真實漲跌。

**影響**：公司行動較多的日期可能被錯判為下跌家數增加，污染 `market_trend_score`，再影響 Strong Bear gate。

**建議修正**：使用後復權收盤價，或直接使用交易所提供、已扣除公司行動影響的漲跌／參考價欄位。

### BUG-13：同一套系統存在兩種 intraday_score 公式

**位置**：

- `app/services/orderflow_intraday.py:90-126`
- `app/services/chip/intraday_score.py`
- `config/thresholds.yaml` 的 `weights.intraday`

`/orderflow` 使用硬編碼的 `0.45／0.35／0.20` 權重，只計算大單、主動買賣與 CVD 斜率；正式 Chip Score 則使用 YAML 中六項盤中因子權重。

**影響**：同一股票可能在 orderflow 頁和 scanner 顯示差異很大的「盤中分數」，且硬編碼權重違反 config 化鐵則。

**建議修正**：若兩者代表不同概念，應改用不同名稱並清楚說明；若都代表盤中籌碼分數，應共用同一純函式與同一份設定。

## 6. P2：邊界與部署問題

### BUG-14：背離掃描可能使用停牌股票的舊資料

**位置**：`app/services/flow_scan.py:72-150`

掃描會處理最近 150 日內出現過的所有股票，沒有要求每檔股票的最後資料日期等於全市場 `as_of`。價格與成交量也沒有套公司行動還原。

**影響**：停牌、下市或近期缺資料股票可能帶著舊價格、舊成交額出現在今日掃描；公司行動也可能製造假的背離。

**建議修正**：只納入最後資料日等於 `as_of` 的股票，並與個股 `/flows` 共用公司行動還原邏輯。

### BUG-15：回測可能把停牌數週後的復牌日當成次一交易日進場

**位置**：`app/backtest/engine.py:61-80`

回測以「該股票在訊號日後的第一根 bar」作為進場點。股票若停牌數週，復牌日仍會被視為有效進場，沒有檢查市場次一交易日、停牌天數、漲跌停或成交可行性。

**影響**：回測可能假設實際策略不會執行的延遲交易，扭曲報酬與 MAE／MFE。

**建議修正**：以市場交易日曆決定預期進場日；該日無可成交行情時應丟棄訊號或依明確規則處理。

### RISK-01：回補 API 沒有身分驗證

**位置**：`app/api/ops.py:194-252`

`POST /api/ops/backfill` 可直接啟動資料回補與 Shioaji 逐筆抓取，沒有 API key、登入或其他授權檢查。CORS 只能限制瀏覽器跨來源請求，不能阻擋直接 HTTP 呼叫。

**影響**：若 API 經反向代理、區網或 Tailscale 對外開放，未授權使用者可能觸發耗時工作與資料配額消耗。若服務始終只綁定受信任 localhost，風險較低。

**建議修正**：所有會改變狀態或消耗外部配額的 ops endpoint 加入管理者認證，並保留操作稽核紀錄。

## 7. 建議修正順序

### 第一批：恢復核心決策正確性

1. BUG-01：重做 RR 的獨立計算方式。
2. BUG-02：Strong Bear 直接使用原始市場趨勢。
3. BUG-03：接入鎖死漲停判斷。
4. BUG-04：定義並接入持倉上下文。

### 第二批：保護每日資料完整性

1. BUG-07：TAIEX／TDCC 改為可觀測的 fail-soft。
2. BUG-08：TPEx 各資料源分開匯入。
3. BUG-09：Shioaji 明確區分空資料與失敗。
4. BUG-10／11：不足視窗與缺資料維持 `NULL`，正確處理成分可用性。

### 第三批：統一驗證與掃描口徑

1. BUG-05：前瞻驗證共用公司行動還原與 Newey–West。
2. BUG-06／14：修正背離快取、日期新鮮度及公司行動還原。
3. BUG-12：修正市場漲跌家數。
4. BUG-13：統一盤中分數定義。
5. BUG-15：加入交易日與可成交性檢查。

### 第四批：部署防護

1. RISK-01：ops 寫入型端點加入認證及稽核紀錄。

## 8. 建議補充的自動化測試

- RR 不應恆等於 `tp1_r`，且必須以預計進場價計算。
- 原始 `market_trend_score=-0.5` 時必須阻擋 BUY，不受市場子分數權重影響。
- 鎖死漲停時不得輸出 BUY。
- 同一股票分別以未持倉／已持倉分析，需覆蓋六種 Action。
- 依序請求背離 `window=60`、`window=20`，兩次結果必須各自正確。
- TAIEX、TDCC、TPEx margin 分別模擬失敗，成功抓取的核心資料仍須落庫。
- Shioaji 空資料、認證失敗、網路失敗必須得到不同狀態與統計。
- 只有 2 筆資料時，5D／20D 特徵應為 `NULL`。
- 法人資料缺漏不能與真正 z-score 0 混為一談。
- 公司行動前後，breadth、背離及 forward return 不得出現機械跳動。
- 停牌股票不得出現在當日掃描，也不得在數週後被回測假設進場。
- 驗證頁與離線 backtest 對同一資料集的報酬、IC 與 Newey–West t 值必須一致。

## 10. 整體判斷

系統的資料分層、成分組合百分位、公司行動價量拆分與 look-ahead 防護方向是合理的，但「分數 → 進場決策 → 驗證」之間仍有幾個尚未閉合的接口。

目前最主要風險不是公式數量不足，而是：

- Entry Filter 中部分 gate 沒有真正使用獨立資訊或根本沒有接線。
- 外部資料源失敗時，系統可能整日停止或把失敗誤認為中性資料。
- 線上驗證與正式 backtest 使用不同的價格還原及統計口徑。

應先修復這些問題，再重新產生歷史特徵與 signal snapshot，最後重跑單調性、MAE、IC 與 Newey–West 檢驗。修正前後的分數與 BUY 數量可能有明顯變化，應視為預期的行為修正，而不是單純的 UI 差異。
